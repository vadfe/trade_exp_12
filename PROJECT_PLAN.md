# План проекта: цель, инструменты, риски и варианты решений

Научить модель извлекать из истории рынка закономерности для полезных торговых сигналов; каждый этап имеет проверяемый результат, готовность инструментов, риски и согласуемые варианты дальнейших действий.

## 1. Цель и границы проекта

Подтверждённая пользователем цель: научить модель извлекать из истории рынка закономерности, позволяющие получать полезные торговые сигналы.

Цепочка: история OHLCV → признаки известного состояния рынка → обучающие примеры «прошлое/будущее» → прогнозная модель → торговые решения → подтверждение на новых данных с издержками и риском.

Признаки не отменяются. Историческая цена является источником и будущей целью, но не заменяет молча весь вход модели. Первый согласованный эксперимент: SBER, 60 минут, признаки 61 известного торгового бара → OHLC трёх следующих торговых баров. Объём известных баров может быть входом; объём будущего не прогнозируется. Три торговых бара не обязательно равны трём календарным часам.

Наличие checkpoint, кластеров, красивых свечей или низкого training loss не означает достижения цели. Практическое преимущество должно быть подтверждено; гарантии будущей прибыли нет.

[x] — инструмент реализован, а не доказана готовность всего этапа. [ ] — инструмент отсутствует либо необходимая проверка ещё не выполнена.

## 2. Общий порядок работы с рисками

При неудовлетворительном результате:
1. Зафиксировать, что именно не прошло: качество данных, корректность реализации, прогноз вне обучения, торговый результат или проверка новых данных.
2. Проверить техническую корректность до смены модели/признаков.
3. Сформулировать одну проверяемую причину и одно изменение. Не менять одновременно признаки, архитектуру, горизонт и торговые правила.
4. До запуска согласовать вариант, метрику, условия успеха, предел числа попыток и остановку. Ранее зафиксированный контрольный вариант сохранять.
5. На разработочной истории сравнить изменение с контрольным вариантом на одинаковых временных разбиениях и простых базах. Список входов/scaler каждого варианта фиксировать отдельно.
6. Просмотренный тест после использования для изменения решения считать частью разработки. Для независимого подтверждения требуются новые неиспользованные исходы/заранее записанные прогнозы.
7. При исчерпании согласованного бюджета без улучшения — остановить текущую гипотезу и обсудить следующий шаг, не запускать бесконечный поиск.

Риски и варианты ниже — карта решений, а не разрешение автоматически реализовать все альтернативы.

## 4. Этап 2 — Признаки и обучающие примеры

### Вход, цель и исходный набор признаков

Текущий FEATURE_COLUMNS в model/dataset.py содержит 33 входных поля. Отправной контракт: вход [61,33], цель [3,4] в порядке open/high/low/close. Любое изменение состава отдельно обосновывается и согласуется.

1. **Форма и движение бара — 5:** log_return = ln(close/previous_close); body_atr = (close-open)/ATR; upper_wick_atr и lower_wick_atr — тени в ATR; range_atr — диапазон в ATR.
2. **Объём — 2:** relative_volume — объём относительно медианы предыдущих 20 баров; volume_spike_10 — относительно среднего предыдущих 10.
3. **Тренд, положение и волатильность — 4:** trend_slope_10/30 — наклоны close в ATR; position_in_range_20 — положение в диапазоне; atr_ratio — ATR7/ATR30.
4. **Импульс и направление — 5:** roc_5/15 — изменение close; consecutive_direction — серия направлений тел со знаком; avg_return_5/10 — средние лог-доходности.
5. **Последовательность форм — 6:** avg_body_atr_5, avg_upper_wick_5, avg_lower_wick_5, avg_range_5 — средние формы; body_deceleration — относительный размер тела; wick_ratio — доля верхней тени.
6. **SMC — 11:** smc_resistance_distance_atr, smc_support_distance_atr; smc_bos, smc_choch; smc_fvg_signal, smc_ob_signal, smc_liquidity_signal; smc_active_bullish_fvg_count, smc_active_bearish_fvg_count, smc_active_bullish_ob_count, smc_active_bearish_ob_count. Используются только события, реально известные к моменту прогноза, не задним числом на pivot.

### Инструменты и готовность
- [x] features/relative.py, market_structure/smc_layer.py — расчёт указанных признаков через pandas/NumPy.
- [x] model/dataset.py, model/dataset_v2.py — существующие окна признаков.

SMC переписан на причинный расчёт (market_structure/causal.py); ретроспективная библиотека давала утечки в BOS/CHOCH/OB/FVG/уровнях.

### Результат и переход
Получаем проверенное числовое описание известного рынка и соответствующие реальные будущие свечи. Переход: подмена будущих raw-данных не меняет вход; времена/цели верны; преобразования обучены только на train и воспроизводимы.

### Риски и решения
| Риск / наблюдаемый признак | Что делаем | Подтверждение |
|---|---|---|
| Признак использует будущее — особенно подтверждения SMC | Prefix-проверка всех полей до самого последнего известного бара, изменение будущих raw-свечей; исправление момента доступности события | Полное совпадение видимых входов при любом изменении будущего |
| Разные масштабы полей, выбросы, NaN/inf искажают обучение | Статистики по train; train-only нормализация, сохранение scaler; осмысленная обработка пропусков с отдельной маской/исключением примера | Паспорт распределений, доля исключений, неизменность scaler при подмене проверки; без молчаливой замены всего нулями |
| После удаления неготовых строк склеиваются несоседние бары | Собирать окна по исходным индексам и проверять непрерывность допущенной последовательности; ночные перерывы отдельно учитывать | Пример сверяется с raw по всем 64 индексам и временам |
| Много дублирующих/шумных признаков | После корректного контрольного запуска проверить удаление одной логической группы, не сразу всех входов | Изменение ошибки вне обучения относительно неизменного контрольного варианта |
| Не хватает контекста режима/сессии/разрыва цены | Согласовать добавление конкретной группы: известное время сессии, разрыв между завершёнными барами, многомасштабный тренд/волатильность | Каждый новый признак причинен и даёт устойчивое улучшение на тех же разработочных разбиениях |
| Цена масштаба/инструмента маскируется под закономерность | Относительные значения и train-only масштабирование; отдельно проверить поведение по ценовым периодам | Преимущество не исчезает целиком при смене уровня цены/режима |

**Риски отдельных групп:** форма бара чувствительна к малому ATR — проверять знаменатели и масштаб; объём меняется по сессиям — проверять базу сравнения, при необходимости согласовать сезонную нормализацию; тренд/импульс дублируются — проверять группы, а не наращивать их вслепую; усреднение форм может сгладить редкие события — отдельно проверить результаты на заранее определённых train-порогами диапазонах; SMC может быть ретроспективным/разреженным — проверять причинность и покрытие событий. Ни один провал не разрешает молча удалить поле.

**Статус:** реализовано и проверено. На реальных данных SBER 60m собрано 32 056 примеров (train 22 448 / validation 4 776 / evaluation 4 706), формы [61,33] → [3,4], причинность подтверждена. Условие перехода к этапу 3 выполнено.

### Результат и переход
Проверяем, извлекла ли модель информацию о будущем. Переходим к сигналам только при устойчивом практически значимом преимуществе над заранее определёнными простыми прогнозами. Метрики/пороги/число попыток фиксируются до запуска. Улучшение high/low не должно скрывать отсутствие пользы close; ошибки компонентов показывать отдельно.

### Риски и решения — порядок диагностики плохого Transformer
| Наблюдение | Возможная причина | Вариант решения и проверка |
|---|---|---|
| Модель не может выучить даже простой предсказуемый синтетический ряд | Ошибка целей, преобразований, loss, загрузки checkpoint либо обучения | Сначала исправить реализацию; проверить прямое/обратное преобразование, градиенты, достижимую синтетическую зависимость. Рыночные эксперименты до исправления запрещены |
| Ошибка мала на train, плоха на следующих периодах | Переобучение, слабая регуляризация либо смена режима | Согласованный вариант меньшей модели/регуляризации, early stopping по validation; оценка по временным блокам и фиксированным seed |
| И train, и validation плохи | Неоптимальное обучение, неверный масштаб цели, недостаток модели или признаков | Проверить оптимизацию/масштабы; затем сравнить с простой моделью на тех же входах. Не делать вывод «нужно больше признаков» до диагностики |
| Простой прогноз лучше, корреляция близка к нулю | Входы могут не содержать устойчивой информации, либо архитектура её не извлекает | Согласовать простой контроль: регуляризованная линейная модель или небольшой MLP на той же истории и OHLC-цели. Если простой вариант лучше — Transformer не обязателен |
| Контрольные модели тоже слабы; есть конкретная гипотеза о недостающем описании рынка | Текущий набор признаков недостаточен | Проверить расширение/изменение ОДНОЙ группы: контекст сессии, ценовой разрыв, другой масштаб тренда/волатильности. Сравнить старый и новый набор с той же архитектурой/разбиением; затем оставить или отвергнуть изменение |
| Часть групп признаков ухудшает обобщение | Шум, дублирование, нестабильность SMC/объёма | Согласованная проверка исключения одной группы, фиксация нового состава только при устойчивом улучшении. Не удалять все признаки по умолчанию |
| Простая модель использует входы, Transformer стабильно проигрывает | Архитектура избыточна или не подходит | Использовать более простую успешную модель; при отдельном согласовании сравнить компактную временную свёртку/другую архитектуру. Одинаковая OHLC-задача и условия оценки |
| Преимущество есть только на одном периоде/seed | Случайность, подгонка, режимная зависимость | Последовательные временные проверки, повторяемость seed, оценка неопределённости; результат не объявлять подтверждённым |
| На всех согласованных вариантах преимущества нет | Задача/источник может не иметь доступной прогнозной информации | Остановить текущую гипотезу. Отдельно согласовать другой горизонт/контекст/данные либо прекращение направления; не обещать, что новая архитектура обязательно поможет |

**Особые риски:** правдоподобные свечи могут быть лишь усреднённой формой — сравнивать с неподвижной ценой и простыми формовыми базами; больше признаков/нейронов может усилить подгонку — польза определяется только вне обучения; неоднократный просмотр test превращает его в разработочную историю — независимость подтверждать на новых исходах.

**Статус:** целевая OHLC-модель реализована и проверена на реальных данных SBER 60m (30 211 баров, ~30k примеров). Результат отрицательный: на отложенной части OHLC MAE 0.175% против 0.188% у неподвижной цены (+7.3%, ниже порога 10%), по close модель равна flat (0.204% vs 0.204%), на горизонте +1 даже хуже. Диагностика простой моделью (Ridge, run_ohlc_ridge.py, те же входы/разбиения): ошибка 0.34% и хуже, рост alpha сходится к flat — линейного сигнала в признаках тоже нет. Две независимые модели не превзошли «цена не изменится». Ворота в этап 4 НЕ пройдены; по плану гипотеза «61×33 → 3 OHLC на SBER 60m» остановлена до согласования изменения (горизонт/контекст/признаки/источник). Последние SBER/GAZP не превзошли неподвижную цену по ошибке close. Их просмотренная история не является новым нетронутым тестом.

Старый модуль использует предсказания разворотов, сумму простых доходностей и не учитывает издержки; он НЕ закрывает этот этап и не заменяет OHLC-задачу.

### Результат и переход
Устанавливаем практическую пользу прогноза. Переход: заранее согласованные требования чистого результата, достаточности сделок и риска выполнены вне участка подбора торговых правил. До прохождения этапа 3 реализацию этой ветки не начинать.

### Риски и решения
| Риск | Вариант решения | Проверка |
|---|---|---|
| Прогноз точнее, но движения малы относительно издержек | Согласовать порог минимального ожидаемого движения/отказ от сделки; если торговля неокупаема — признать отсутствие сигнала | Чистый результат с полными издержками против отсутствия сделок |
| Выгодны только отдельные прогнозы, а общая точность не отражает прибыль | Проверить заранее определённый фильтр амплитуды/уверенности на разработочной части, не выбирать сделки по известному исходу | Число сигналов, доходность и риск на отдельной проверке |
| Нереалистичные входы по уже прошедшей цене | Вход не раньше реально доступного исполнения после сигнала; учитывать спред/задержку | Журнал времён сигнала и исполнения, проверка каждого типа сделки |
| По OHLC неизвестно, что внутри бара было раньше: стоп или цель | Не угадывать порядок в пользу стратегии: консервативная оценка либо отдельно согласованные более мелкие данные | Отдельный отчёт неоднозначных сделок и чувствительности |
| Порог/стопы подобраны под историю | Ограниченный заранее согласованный набор правил и отдельная оценочная часть | Фиксированные правила до проверки и сохранённые отклонённые варианты |
| Прибыль получена несколькими событиями, просадка неприемлема | Анализ концентрации результата и размеров риска; согласованное ограничение позиции | Результат по периодам, вклад крупнейших сделок, просадка |

**Статус:** целевой инструмент не реализован. Торговые условия/риски согласовываются до реализации, а не придумываются агентом.

## 7. Этап 5 — Подтверждение на новых данных

### Инструменты и готовность
- [ ] Получение новых завершённых свечей и прогноз фиксированной моделью с теми же признаками/scaler.
- [ ] Журнал прогнозов/сигналов ДО появления исходов, версии модели и торговых правил.
- [ ] Виртуальное исполнение, последующая сверка, чистый результат и риск.

### Результат и завершение
Отделяем реальный эффект от подгонки истории. Цель считается подтверждённой только при выполнении заранее согласованных требований на установленном объёме новых наблюдений без подгонки. До этого — кандидат. Реальная торговля/автоматизация — отдельное решение пользователя, не автоматическое продолжение.

### Риски и решения
| Риск | Вариант решения | Проверка |
|---|---|---|
| На новых данных преимущество исчезает | Проверить качество поступления и смену распределений; при исправном pipeline остановить сигналы, затем отдельно согласовать пересмотр модели | Отдельно различать поломку данных и провал прогнозной гипотезы |
| Исходов/сделок слишком мало | Накопить заранее согласованный минимум, не выдавать несколько удачных сделок за подтверждение | Число наблюдений, неопределённость, статус «данных недостаточно» |
| Изменили признаки/scaler/модель во время проверки | Версионировать и заморозить комплект; новая версия начинает отдельную проверку | Manifest и журнал времени каждого изменения |
| Пропущены данные/запуск, прогноз записан задним числом | Контроль времени доступности и сохранения, пропуски явно помечать; не дописывать выдуманные исторические сигналы | Неизменяемый журнал событий и видимые пропуски |
| Хороший исторический сигнал деградирует | Мониторинг заранее заданных критериев остановки; переобучение только отдельной версией с новой проверкой | Отчёт деградации, остановка при нарушении лимитов |

**Статус:** не реализован.

| Общий риск | Правило решения |
|---|---|
| Снова подменить задачу близкой, но другой | Проверять контракт «источник → признаки входа → будущая цель → метрика → вклад в сигналы»; смена только после согласования |
| Код выполнен, но результат нельзя проверить | UI и выгрузка данных обязательны для каждого этапа; никаких артефактов только на диске |
| Несохранённый буфер IDE отличается от проверенного кода | Проверять дисковую версию и diff перед тестами/публикацией, разрешать конфликт без потери пользовательских правок |
| Обновление ломает БД/версии/пути | Не коммитить и не откатывать серверный реестр, не удалять исходные данные; переносимые пути и совместимость протоколов |
| Успешные unit-тесты скрывают неработающий UI/процесс | После программного этапа pytest + Ruff + реальные HTTP-проверки всех изменённых страниц/API и короткого полного пути на доступных данных |
| Затраты на бесконечные эксперименты | До старта фиксировать бюджет вариантов и критерий остановки; каждый вариант отвечает на одну гипотезу |

## 9. Сдача и управление изменениями

После этапа кратко: что получили; что это доказывает; прошли/не прошли ворота; точные команды/клики; ограничение и следующее действие. Пользовательские команды — с серверной .venv; агент проверяет через .venv-devin и не выдаёт свой временный сервер за пользовательский.

Никаких изменений кода в режиме планирования. Этот документ фиксирует цель, этапы, состояние и ветви решений, но не разрешает автоматически реализовать все перечисленные альтернативы. Конкретная реализация — только после утверждения через exit_plan_mode.
